Why This Exists

One Million Checkboxes is intentionally simple at the product layer and intentionally difficult at the systems layer. The public interaction is one bit per item, but the operational challenge is global consistency under bursty, concurrent traffic with strict UI responsiveness requirements.

Frontend Architecture

Rendering one million native inputs directly would overwhelm layout, memory, and input processing. The UI instead uses a virtualized window: only checkboxes that intersect the viewport (plus a small row buffer) exist in the DOM at any time. Everything else remains logical state only.

  • Virtualized grid math converts checkbox IDs to row and column coordinates using fixed pitch (`itemSize + gap`).
  • The render engine clamps viewport bounds and row windows to prevent empty first paint and edge clipping.
  • State arrives incrementally and is merged into an in-memory map keyed by checkbox ID.
  • Visible refreshes are scheduled on animation frames to avoid long main-thread blocks.
  • User writes are debounced and batched to reduce network chatter and backend amplification.
  • Startup avoids stale scroll restoration and forces first-paint checks to guarantee visible content.

Backend Architecture

The backend runs on a single Cloudflare Worker with a Durable Object that acts as the authoritative room for checkbox state. All state lives in one globally-consistent object instance — Cloudflare routes every request to it regardless of the originating edge location. Each checked item is stored as a compact c:{id} key in Durable Object SQLite storage, and writes are serialized by the single object instance to prevent cross-region race conditions.

  • GET /api/checked — returns the full checked ID set for initial sync, paginated over SQLite keys.
  • POST /api/update and POST /api/batch — apply mutations atomically inside the room. The batch endpoint accepts up to hundreds of state changes in one round-trip, which the frontend uses to flush debounced writes.
  • GET /api/events — opens a Server-Sent Events (SSE) stream. The Durable Object holds an in-memory set of open response writers; every mutation triggers a broadcast to all connected clients simultaneously.
  • SSE was chosen over WebSockets deliberately: it is unidirectional (server → client), lower overhead, and reconnects automatically via the browser's native EventSource API — well-matched to a read-heavy realtime feed.
  • CORS is open on all endpoints so the static GitHub Pages frontend can call the worker API without a proxy.

Consistency and Throughput Tradeoffs

This system targets practical eventual consistency for a highly interactive shared surface. Immediate local updates provide low latency UX, while stream updates reconcile remote mutations. The design favors responsiveness and operational simplicity over strict transaction semantics across all clients.

  • Local optimistic state makes interactions feel instant.
  • Realtime stream applies remote deltas to keep peers aligned.
  • Batch writes smooth request spikes and reduce rate-limit risk.
  • Virtualized rendering keeps memory and layout cost bounded even at million-item scale.

Why It Matters

The app demonstrates that apparent simplicity can hide non-trivial engineering: data modeling for bit-state at scale, network fan-out design, client render constraints, and resilient startup behavior under real-world browser timing. It is a minimal interface backed by distributed-systems thinking.
